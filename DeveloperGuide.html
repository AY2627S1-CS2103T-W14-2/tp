LinkUp Developer Guide

Acknowledgements

LinkUp builds on se-edu AddressBook Level 3. The layered architecture, command infrastructure, and parts of this documentation originate from that project. The application uses JavaFX for its interface and Jackson for JSON storage; dependencies and versions are declared in build.gradle. Documentation is built with MarkBind.

Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

How the Logic component works:

  1. When Logic is called upon to execute a command, it passes the text to AddressBookParser. Commands with structured arguments use a matching parser (e.g., DeleteCommandParser); commands such as list, help, and undo are constructed directly.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Here are the other classes in Logic (omitted from the class diagram above) that are used for parsing a user command:

How the parsing works:

  • For commands with structured arguments, AddressBookParser creates an XYZCommandParser (XYZ stands for the command name, e.g., Add). That parser validates arguments and returns an XYZCommand object as a Command.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Model component

API : Model.java

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • exposes a FilteredList<Person> backed by the address book's observable list. Changing its predicate updates the displayed results without removing contacts from the underlying address book.
  • stores a UserPrefs object containing GUI settings. This is exposed to the outside as a ReadOnlyUserPrefs object.
  • keeps undo snapshots in an in-memory Deque<AddressBook>; they are not stored in JSON.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Current command and contact model

The MVP includes add, list, find, findproject, project, delete, clear, undo, help, and exit, with same-name support, duplicate-detail validation and persistence. edit was outside the MVP release and now goes beyond it, covering name, phone, email and Telegram username; see Edit command implementation.

The Java package remains seedu.address, and internal names such as AddressBook are retained from AB-3. AddressBookParser dispatches add, edit, delete, clear, find, findproject, list, project, undo, help, and exit. Command words are case-sensitive.

AddCommandParser requires exactly one each of n/, p/, e/, tele/, and pr/. It constructs a Person with one initial project. Subsequent project commands append associations. EditCommand can replace the name, phone, email and Telegram username, and always keeps the contact's projects. EditCommandParser accepts n/, p/, e/, and tele/, requires at least one of them, and rejects pr/. Replacing or removing projects is deferred. Unsupported prefixes are not a general extension mechanism: unrecognised text can become part of another field's value, so callers must use the documented grammar.

Value class Current new-input rule and normalisation
Name 1–60 characters, at least one English letter; English letters, digits, spaces, apostrophes, hyphens and periods. Surrounding spaces are trimmed.
Phone Leading +, 3–15 digits with a non-zero first digit; accepted internal spaces and hyphens are removed. No country code is inferred.
Email One @, non-empty dot-separated local parts, and at least two valid domain labels; no whitespace. Stored in lowercase.
TelegramUsername 5–32 Latin letters, digits or underscores; optional leading @ is removed and letters are lowercased.
Project 1–40 Unicode code points after whitespace normalisation; no ISO control characters. Equality ignores case.

JsonAdaptedPerson restores names, phones and emails through their stored-value validation paths, preserving legacy spelling and phone formats. Missing Telegram usernames become TelegramUsername.EMPTY; missing projects become an empty list. These compatibility rules do not make those fields optional in new add input.

Name search and displayed indices

FindCommandParser trims surrounding whitespace and rejects blank input or more than 60 Unicode code points before splitting keywords on whitespace. NameContainsKeywordsPredicate compares lowercase text using Locale.ROOT and matches any keyword as a substring (OR semantics), including partial words. For example, find lex vid can match Alex and David. Each contact appears once in saved order.

Both search commands replace the predicate on the full address book rather than searching only the previous results. delete, edit, and project resolve one-based indices against the displayed list. add, a successful edit, list, and successful undo show all contacts; delete, project, and a failed or unchanged edit retain the active filter. After a mutation, indices can change, so callers must read the current list before using another index.

Removing retired contact fields

Person contains name, phone, email, Telegram username, and an ordered list of projects. Address and tags have been removed from the model, contact cards, and JSON output. AddCommandParser and EditCommandParser recognize the old a/ and t/ delimiters only to reject them with ParserUtil.MESSAGE_REMOVED_CONTACT_FIELDS; this prevents old arguments from becoming another field's value. These delimiter sequences following a space remain reserved in add/edit input.

JsonAdaptedPerson ignores old address/tag properties through the existing Jackson unknown-property configuration. Missing Telegram usernames and projects retain their legacy defaults. Before saving, JsonAddressBookStorage.backupLegacyData inspects the existing file for retired fields and writes its original bytes to a unique sibling .pre-v1.3-<unique suffix>.bak file. It also backs up malformed JSON before replacement. A backup I/O failure propagates before any overwrite. After a successful migration, subsequent saves find no retired properties and create no further backup. Backup files are not part of command undo history.

A file that is well-formed but cannot be loaded, for example because two contacts conflict, may have no retired fields and therefore may not qualify for the migration backup. When MainApp.initModelManager catches the DataLoadingException and starts with an empty address book, it calls Storage#backupAddressBook(), which copies the file to a unique sibling .unreadable-<unique suffix>.bak file before the first save can replace it. If the backup fails, initModelManager rethrows the IOException and init() stops before creating Logic or the UI, so no save can replace the only copy; start() then shows an error dialog asking the user to copy the file somewhere safe and fix the problem, and exits. LinkUp starts with an empty address book only after a successful backup. MainAppTest covers both outcomes. The backup is made only at startup, not on every read, so tests and other callers of readAddressBook do not create backup files.

Regression tests cover legacy loading, the save/load round trip, exact backup contents, repeated saves, backup failure, and former-prefix rejection. Existing edit, project, search, and undo tests exercise the updated contact structure. New add commands require an initial project; legacy contacts can still have an empty project list.

Duplicate contact detection

Two contacts conflict if they share a phone number, an email or a Telegram username. Names and projects are never compared, so contacts may share a name. The rule lives in one place, Person#findConflictWith(Person), which checks phone, email and Telegram username in that order and returns the first clash as a ContactConflict (the clashing field, the value and the existing contact). ContactConflict#getMessage() builds the only user-facing duplicate message. Person#conflictsWith(Person) is the boolean form.

  • Newly entered emails are stored in lower case, but emails saved by older versions keep their case. Email#equals and Email#hashCode therefore compare the lower-cased (Locale.ROOT) text, so a saved Bob@Example.com still clashes with a new bob@example.com. TelegramUsername is already normalised to lower case without @ when it is constructed.
  • Phones are compared in their saved form. New numbers are stored as + followed by digits, so spaces or hyphens never hide a clash. A legacy local number such as 91234567 does not match +6591234567, because LinkUp never infers a country code. An empty Telegram username (TelegramUsername.EMPTY, used by legacy contacts) never matches.
  • UniquePersonList checks every add, setPerson and setPersons call and throws DuplicatePersonException carrying the conflict message. setPerson(target, editedPerson) ignores target, so a contact never conflicts with its own old values, while a clash with any other contact is still caught.
  • Model#findConflict(candidate) and Model#findConflict(candidate, excluded) expose the check. AddCommand uses the first; EditCommand passes the contact being edited as excluded. Both reject a conflict through Command#rejectIfConflicting, before the model is changed. JsonSerializableAddressBook rethrows a conflict found while loading as an IllegalValueException with the same message.
  • The relation is symmetric but not transitive: A may share a phone with B and B an email with C, while A and C do not conflict. It is therefore not an equality. Person#equals remains the all-fields check used to find and remove a contact, which keeps lookup working for contacts with the same name.

Alternatives considered:

  • Keep isSamePerson, redefined as "all fields equal". This would still let two contacts share a phone or email under different names, and it would duplicate equals. It was removed instead.
  • Lower-case every saved email when loading. This would make a case-sensitive comparison enough, but it would silently rewrite emails saved by older versions. Comparing case-insensitively handles both old and new emails.
  • Warn about, rather than reject, a contact with the same name. Names do not identify people, and a warning on every same-name contact would add noise without preventing real duplicates.

Tests build clashes with ConflictTestUtil#clashesWith. EditCommandTest#UNIQUE_FIELD_EDITS lists the editable unique fields (phone, email and Telegram username); when another unique field becomes editable, adding one entry there tests that it is rejected on a clash with a visible or hidden contact, and that the contact's own value is not a clash when another field changes.

Finding contacts by project

The findproject KEYWORD command implements UC02 using the existing filtered contact list.

  1. AddressBookParser routes findproject to FindProjectCommandParser.
  2. The parser removes surrounding whitespace, rejects a blank phrase, and checks the 40-character limit before collapsing internal whitespace. Length is measured in Unicode code points, consistent with the project model. The surrounding-whitespace rule covers the same whitespace and Unicode separator characters as Project.normalize().
  3. ProjectContainsKeywordPredicate uses Project.normalize() and Locale.ROOT to normalise the search phrase once. It checks whether any project returned by Person.getProjects() contains that whole phrase, ignoring case.
  4. FindProjectCommand passes the predicate to Model.updateFilteredPersonList(...) and returns the result count or a specific no-matches message. The UI observes this list and displays the existing contact cards and indices.

The predicate filters contacts rather than collecting a result for each matching project, so a contact appears at most once. Replacing the predicate searches the full underlying address book, even after another search has filtered the displayed list. list restores all contacts; delete continues to use the displayed indices. Search does not change contacts or project associations. LogicManager retains its normal save-after-command behaviour, saving the complete address book rather than just the search results. Invalid input fails during parsing, before the filter or saved data is changed.

Both the search keyword limit and the stored project-name limit are 40 Unicode code points. The search parser checks length before collapsing internal whitespace, whereas Project validates the normalised name. The parser therefore validates the search phrase separately from ParserUtil.parseProject().

Design choices: A separate command preserves the existing name-search behaviour. Whole-phrase substring matching supports partial project names without treating individual words as alternatives. Reusing the model's existing filter avoids introducing a separate project index or changes to storage and the UI.

Project association implementation

The project INDEX pr/PROJECT command implements UC03. AddressBookParser delegates to ProjectCommandParser, which parses the displayed index and requires exactly one project prefix. ParserUtil.parseProject reuses the shared Project validation and normalisation rules.

ProjectCommand resolves the index against Model.getFilteredPersonList(), checks whether the normalised project already exists, and copies the contact's immutable project list before appending the new project. It constructs a replacement Person with all other fields preserved and calls Model.setPerson. Keeping the active predicate preserves the user's search context.

Projects are stored as an ordered list to retain display order. Duplicate detection uses Project.equals, so casing and redundant whitespace do not create separate associations. Invalid indices and duplicate associations throw CommandException before any model mutation; malformed arguments throw ParseException.

The existing LogicManager saves the updated address book through JSON storage after execution. No new storage format or UI component is required: both already support a contact's project list. Command tests cover filtered indices, preservation of fields and order, and duplicate rejection. Parser tests cover malformed input and length boundaries. An integration test exercises command dispatch, filtered selection, rejected operations, and a JSON round trip.

Edit command implementation

edit INDEX [n/NAME] [p/PHONE] [e/EMAIL] [tele/TELEGRAM] replaces one or more details of the contact at a one-based index in the displayed list. EditCommandParser validates each supplied value with the same ParserUtil methods as add and stores it in an EditCommand.EditPersonDescriptor. It reports one problem at a time, in this order: retired a/ or t/, any pr/ (with EditCommand.MESSAGE_PROJECT_NOT_EDITABLE), the index, repeated prefixes (even with identical values), the supplied values (name, phone, email, Telegram username), and finally a missing field. The parser never reads the model. A field left unset in the descriptor is kept exactly as saved, so untouched legacy values (for example a local phone 91234567 or a mixed-case email) are not normalised, and a legacy contact is never forced to supply a Telegram username or project.

EditPersonDescriptor#setTelegramUsername rejects TelegramUsername.EMPTY with an IllegalArgumentException: a Telegram username cannot be cleared, so a parser or helper bug fails loudly instead of wiping it. null means "not supplied". EditCommand also defines MESSAGE_PROJECT_NOT_EDITABLE, for the parser to report pr/.

EditCommand#execute checks, in order:

  1. The index is within the displayed list, or it reports Messages.MESSAGE_INVALID_PERSON_DISPLAYED_INDEX.
  2. It builds the complete replacement Person: supplied fields replace, omitted fields and the ordered project list are copied.
  3. If every saved string (Name#fullName, Phone#value, Email#value, TelegramUsername#value) is unchanged, it throws No changes made. Saved strings are compared instead of Person#equals because Email#equals ignores case: re-entering a legacy Alex@Example.com as alex@example.com is a real change. A Telegram username entered as @Alice_Tan normalises to alice_tan, so it is unchanged if that is the saved value.
  4. Model#findConflict(editedPerson, personToEdit) checks the whole address book, including contacts hidden by the filter, and Command#rejectIfConflicting reports the first clash. Unchanged values cannot clash, so the no-change check runs first.
  5. Model#setPerson replaces the contact once and the filter is reset to show all contacts.

Every rejection is a CommandException thrown before the model changes. Because LogicManager records an undo snapshot and saves only after a command returns normally, a failed or unchanged edit leaves contacts, the filter, the saved file and the undo history as they were, without any change to LogicManager. One successful edit, whatever the number of fields, is one undo step.

Alternatives considered:

  • Treat an unchanged edit as a successful command. It would save the file and push an undo snapshot that undoes nothing, so the next undo would appear to do nothing. It was rejected.
  • Apply the valid fields and report the invalid ones. Partial edits are hard to notice and undo, so the whole command is rejected instead.

EditCommandTest covers each field, legacy values, filtered indices, conflicts with visible and hidden contacts, no-change detection and filter handling. EditCommandParserTest covers the parse order above. EditCommandIntegrationTest types edit commands, including tele/ and pr/, through the real parser, LogicManager and JSON storage, checking saved data, reloads, save counts, the filter and undo.

Undo command implementation

The undo command restores the address book to the state before the most recent successful command that supports undo and has not already been undone. It supports add, edit, delete, clear, and project. Previous states are kept in a stack, so repeated undo commands reverse changes in reverse execution order.

When LogicManager.execute(...) receives a command, it checks Command.isUndoable(). For an undoable command, it copies the current address book before execution. If execution succeeds, LogicManager saves that copy through Model.saveUndoState(...), pushing it onto ModelManager's Deque<AddressBook> undo history. Commands that are not undoable and commands rejected during parsing or execution will not be added to the undo history.

When undo is invoked and undo history is not empty, LogicManager first saves Model.getUndoState() to storage. If that save fails, the contact list, filter, and history remain unchanged, allowing the user to retry. UndoCommand checks Model.canUndo() before restoring anything. If a snapshot exists, ModelManager.undo() restores the most recent snapshot with AddressBook.resetData(...), removes only that snapshot from the undo history, and updates the filtered person list to show all contacts. If no snapshot exists, the command reports No command to undo.

The undo history is held only in memory and is not persisted, so it is unavailable after restarting the application. A new undoable command after an undo adds a snapshot of the current state while preserving earlier history. There is no redo command.

Persistence and save failures

Apart from the special undo path above, LogicManager saves the complete address book after each command executes successfully, including find, findproject, and list. Parsing and validation failures do not save. The data path is data/addressbook.json, relative to the launch folder; preferences.json records GUI settings. Both paths are constants in MainApp. Shutdown saves preferences, not a separate copy of contact data.

A failed save is reported as a CommandException, with a separate message for access-denied errors. Ordinary mutations are not rolled back on disk-write failure: the UI can contain an unsaved change and its undo snapshot. After fixing storage, a successful command such as list retries saving the current state. This differs from validation failure, which leaves contacts unchanged.

Deferred features

Editing, removing or renaming project associations, notes, roles, sorting, archiving, and redo are not implemented. The user stories below include backlog ideas; they are not claims about commands available in this release. No archiving design has been implemented yet.

Appendix: Requirements

Product scope

Release boundary: All ten commands listed in the current command model were in the MVP release. edit was excluded from MVP acceptance and has since been extended as post-MVP work. Other future user stories below are not commitments.

Target user profile:

  • is a student who works on multiple courses or projects and needs to manage classmates, teammates, and other project contacts
  • needs to keep contact details such as names, phone numbers, email addresses, Telegram usernames, and project associations together in one place
  • prefers a lightweight desktop application and is reasonably comfortable with keyboard-driven CLI commands
  • values quick contact lookup and updates over navigating a feature-heavy contacts application

Value proposition: LinkUp helps students quickly add, organize, and retrieve project-related contacts and their details from one keyboard-driven address book, reducing the need to search across separate course or project contact lists.

Use cases

The following use cases describe the currently implemented workflows of LinkUp. For all use cases, the System is LinkUp and the Actor is a student managing project contacts. The application is running. MSS stands for Main Success Scenario.

UC01: Find a project mate by name

MSS

  1. Student requests to search for contacts using a name keyword.
  2. LinkUp displays contacts whose names contain any whitespace-separated keyword, ignoring case and allowing partial-word matches, together with their contact details and projects. Matching uses OR semantics and preserves the existing contact order without duplicate results.
  3. Student uses the displayed project information and contact details to identify the intended project mate.

Use case ends.

Extensions

  • 1a. The search input is empty or exceeds 60 Unicode code points after trimming surrounding whitespace. Internal whitespace counts towards the limit before splitting the input into keywords.

    • 1a1. LinkUp displays an error message without changing saved contacts or the displayed results.

    Use case resumes at step 1.

  • 2a. No contacts match the keyword.

    • 2a1. LinkUp displays a message indicating that no contacts were found.

    Use case ends.

UC02: Find contacts belonging to a project

MSS

  1. Student requests to search for contacts using a project keyword.
  2. LinkUp displays contacts associated with projects whose names contain the keyword, ignoring case.
  3. Student reads the displayed contact details and project information to find the relevant project mates.

Use case ends.

Extensions

  • 1a. The keyword is empty or exceeds 40 characters after trimming surrounding spaces.

    • 1a1. LinkUp displays an error message without changing saved contacts.

    Use case resumes at step 1.

  • 2a. No contacts belong to a matching project.

    • 2a1. LinkUp displays a message indicating that no contacts were found for the project keyword.

    Use case ends.

UC03: Associate an existing contact with a project

MSS

  1. Student requests to list contacts.
  2. LinkUp displays the saved contacts with their indices, contact details, and projects.
  3. Student requests to associate a contact at a displayed index with a project, supplying the project name.
  4. LinkUp adds the project association to that contact, preserves its existing project associations, and displays a success message.

Use case ends.

Extensions

  • 2a. There are no saved contacts.

    • 2a1. LinkUp displays a message indicating that no contacts have been saved.

    Use case ends.

  • 3a. The index is missing, is not a positive integer, or does not refer to a contact in the displayed list.

    • 3a1. LinkUp displays an index error without changing saved contacts.

    Use case resumes at step 3.

  • 3b. The project name is missing or invalid, or the project parameter is repeated.

    • 3b1. LinkUp displays the relevant input error without changing saved contacts.

    Use case resumes at step 3.

  • 3c. The contact is already associated with the same normalised project.

    • 3c1. LinkUp displays a message indicating that the association already exists, without changing saved contacts.

    Use case resumes at step 3.

UC04: Delete a contact

MSS

  1. Student requests to list contacts.
  2. LinkUp displays the saved contacts with their indices, contact details, and projects.
  3. Student identifies the contact to remove and requests its deletion using its displayed index.
  4. LinkUp deletes only the selected contact and displays a success message.

Use case ends.

Extensions

  • 2a. There are no saved contacts.

    • 2a1. LinkUp displays a message indicating that no contacts have been saved.

    Use case ends.

  • 3a. The index is missing, is not a positive integer, or does not refer to a contact in the displayed list.

    • 3a1. LinkUp displays an index error without deleting any contact.

    Use case resumes at step 3.

UC05: Add a contact

MSS

  1. Student requests to add a contact, supplying a name, phone number, email, Telegram username and one initial project.
  2. LinkUp saves the contact and displays a success message with its details.

Use case ends.

Extensions

  • 1a. A required detail is missing or invalid.

    • 1a1. LinkUp displays the relevant input error without changing saved contacts.

    Use case resumes at step 1.

  • 1b. The phone number, email or Telegram username is already used by another contact. Emails and Telegram usernames are compared ignoring case; names and projects are not compared.

    • 1b1. LinkUp names the first clashing detail, in the order phone number, email, Telegram username, and the contact that uses it, without changing saved contacts.

    Use case resumes at step 1.

Non-Functional Requirements

These are design targets, not a claim that performance or usability benchmarks have been completed. CI exercises Windows, macOS and Linux with Java 25; other OS/JDK combinations are not verified by that matrix.

  1. Environment: The supported release setup is Windows, macOS or Linux with Java 25 installed.
  2. Capacity: The system shall support at least 1000 saved contacts without noticeable sluggishness during typical usage.
  3. Performance: The system shall return results within 2 seconds when searching using name or project for a contact list of up to 1000 contacts.
  4. Usability: The system shall display a clear success message or a specific error message after every command.
  5. Interaction efficiency: A user with above-average typing speed for regular English text should be able to complete most tasks faster using commands than using mouse interactions.
  6. Data integrity: If a command fails because of invalid input, an invalid index, or a duplicate, the system shall leave the contact list unchanged.
  7. Data consistency: The system shall validate and normalise contact and project data consistently before storing or searching it.
  8. Persistence and reliability: Contacts should survive restart after a successful save. An unreadable data file is backed up before starting empty; if backup fails, startup stops with an error dialog. Ordinary save failures report an error but may leave unsaved changes in memory, as described above.

Glossary

  • Contact: A saved record for a project mate, containing their name, contact details, and associated projects.
  • Project: A module project or team that a contact belongs to, such as CS2103T or Orbital.
  • Project association: A link between a contact and a project. A contact can be associated with more than one project.
  • Displayed contact list: The contacts currently shown in LinkUp, including results of a search.
  • Index: A one-based number identifying a contact in the currently displayed contact list.
  • Same-name disambiguation: Using project information to distinguish contacts with identical or similar names.
  • Mainstream OS: Windows, Linux, Unix, or macOS.

Appendix: Instructions for manual testing

Use a separate writable test folder with Java 25 and a freshly built LinkUp.jar. These steps modify test contacts and files. Keep real contact data outside this folder. Record the commit, OS, Java version, commands, expected and actual results when reporting a failure. The cases below are a repeatable starting point for exploratory testing, not a claim that every platform has been manually tested.

Launch, shutdown and persistence

  1. From the empty test folder, run java -jar LinkUp.jar in a terminal. Expect sample contacts.
  2. Run list. Expect all sample contacts and Listed all contacts.; the command also saves the data.
  3. Resize and move the window, then run exit. Relaunch from the same folder. Expect the saved contacts and window settings to return. Check data/addressbook.json and preferences.json in this folder.
  4. Run undo immediately after restart. Expect No command to undo. because history is session-only.
  5. Run help. Expect the help window; close it and continue entering commands in the main window.

Prepare deterministic contacts

Run these commands in order in the test instance:

clear
add n/Alex Tan p/+65 9123-4567 e/ALEX@Example.COM tele/@Alex_Tan pr/Team Alpha
add n/Alex Tan p/+65 8765-4321 e/OTHER@Example.COM tele/@Other_Alex pr/Orbital
add n/David Lim p/+65 8111-2222 e/david@example.com tele/david_lim pr/Team Beta

Expect three contacts in that order, including two separate Alex Tan cards. Phones display without spaces or hyphens, emails are lowercase, and Telegram usernames display a leading @. Projects distinguish the namesakes.

Search, index selection and editing

Run the following in order after preparing the contacts:

Input Expected result
find LEX vid Three contacts: case-insensitive partial keywords use OR matching.
findproject team alpha Only the first Alex Tan.
find vid David Lim, proving search starts from the full address book.
edit 1 n/David Lee David is renamed; all three contacts are displayed again.
findproject Orbital Only the second Alex Tan, shown at index 1.
project 1 pr/Team Alpha Adds a second project to this Alex and retains the Orbital filter.
project 1 pr/ team ALPHA Duplicate project error; associations unchanged.
findproject Team Alpha Both Alex contacts, once each.
findproject Alpha Team No matches: project search uses a whole phrase, not OR keywords.
find Format error; previous results remain unchanged.
list All three contacts return in saved order.
delete 0 then delete 4 Invalid-index errors; all contacts remain.
findproject Orbital then delete 1 Only the second Alex is deleted.
undo The deleted Alex returns, in original order; all contacts are shown.

Editing contacts

Continue after the preceding sequence, with Alex Tan, Alex Tan and David Lee displayed. Run in order:

Input Expected result
find David then edit 1 n/David Lee No changes made.; only David is still shown and nothing is saved.
edit 1 n/David Lim p/+65 8111-3333 e/David.Lim@Example.com Edited contact: David Lim; Phone: +6581113333; Email: david.lim@example.com; ...; all three contacts are shown and the project is kept.
edit 3 n/David Lim No changes made.; no undo step is added.
undo Name, phone and email all return to David Lee's previous values in one step.
find Lee then edit 1 p/+6591234567 Phone conflict with the first Alex, although that contact is hidden; only David is still shown.
edit 1 n/Dave e/ Invalid email; the name is not changed either.
list All three contacts, with David's details unchanged.

Continue with Telegram usernames and projects:

Input Expected result
edit 3 tele/@David_L n/David Lim Both fields change; the Telegram username is saved as david_l.
edit 3 tele/@DAVID_L No changes made.: it normalises to the saved david_l.
edit 3 tele/ Telegram username format error; nothing changes, because a Telegram username cannot be cleared.
edit 3 tele/@alex_tan Telegram conflict with the first Alex.
edit 3 n/David pr/Team Beta Projects cannot be edited with edit. Use project INDEX pr/PROJECT to add an association.; nothing changes.
undo David Lee's name and Telegram username return, restoring the fixture for the next section.

Use project to append a project.

Validation and duplicate rejection

Start with list after the preceding sequence. Each rejected command below must leave the contacts unchanged:

Input Expected result
add n/New Person p/+6591234567 e/new@example.com tele/new_person pr/Test Phone conflict with the first Alex.
add n/New Person p/+6599998888 e/ALEX@EXAMPLE.COM tele/new_person pr/Test Email conflict, ignoring case.
add n/New Person p/+6599998888 e/new@example.com tele/@ALEX_TAN pr/Test Telegram conflict, ignoring case and @.
add n/New Person p/+6599998888 e/new@example.com tele/new_person Required-project error.
add n/New Person p/99998888 e/new@example.com tele/new_person pr/Test Invalid new phone: a leading + is required.
edit 3 e/other@example.com Email conflict with the second Alex.
edit 1 a/Old Address Address/tags are no longer supported.
edit 1 n/Alex Tan n/Another Name Duplicate-prefix error.

For boundaries, try find with 60 and then 61 consecutive x characters, and findproject with 40 and then 41. The shorter query is accepted (with no matches); the longer one reports a length error without changing the current results. Run list to restore the displayed contacts. Then project 1 pr/ with 40 consecutive x characters succeeds, while 41 fails. Run undo after the accepted project change to restore the fixture.

Undo and restart

  1. Run list, then clear. Expect an empty list; list now reports No contacts saved yet.
  2. Run undo. Expect the three contacts to return. list has not consumed or added an undo entry.
  3. Run edit 1 n/Alex Updated, then undo. Expect the original name and all contacts.
  4. Run exit and relaunch from the same folder. Expect the restored contacts and undo to report no history.

Missing, unreadable and legacy files

Close the application before each file change, and keep a valid copy outside the test folder. Restore that valid copy before each scenario so the legacy tests start with contacts rather than the preceding empty file.

Scenario Procedure and expected result
Missing data Move data/addressbook.json out of the test folder. Relaunch: sample contacts appear. Run list to save them.
Malformed JSON Replace the test data file with {. Relaunch: an empty list appears after a sibling .unreadable-<unique suffix>.bak backup is created. Verify that backup contains exactly { before running list, which saves an empty address book.
Legacy fields In a valid saved contact, add "address": "Old Address" and "tags": ["old"]. Relaunch and run list: the saved contact omits these fields, and a sibling .pre-v1.3-<unique suffix>.bak preserves the original file. A second list creates no further migration backup.
Legacy missing fields Remove telegramUsername and projects from one valid contact. Relaunch: it loads without a Telegram username or project. New add commands still require both.

Backup and permission failures depend on the OS and account. Their automated coverage is in MainAppTest, JsonAddressBookStorageTest, and LogicManagerTest. If reproducing them manually, use only the test folder: when startup cannot back up unreadable data, expect an error dialog and no main window; when an ordinary save fails, expect an error even though the in-memory change may already be visible. Fix storage and run list to retry saving. A failed undo save must preserve contacts, the filter, and undo history so undo can be retried.
