Acknowledgements

LinkUp builds on se-edu AddressBook Level 3. The layered architecture, command infrastructure, and parts of this documentation originate from that project. The application uses JavaFX for its interface and Jackson for JSON storage; dependencies and versions are declared in build.gradle. Documentation is built with MarkBind.

Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, RecentFindPanel, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

RecentFindPanel displays names, Telegram usernames, and project tags in a compact, independently scrolling list above PersonListPanel. Its container has a fixed height of 160 pixels; the main person-list container has a minimum height of 180 pixels and grows with the window.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

How the Logic component works:

  1. When Logic is called upon to execute a command, it passes the text to AddressBookParser. Commands with structured arguments use a matching parser (e.g., DeleteCommandParser); commands such as list, help, and undo are constructed directly.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Here are the other classes in Logic (omitted from the class diagram above) that are used for parsing a user command:

How the parsing works:

  • For commands with structured arguments, AddressBookParser creates an XYZCommandParser (XYZ stands for the command name, e.g., Add). That parser validates arguments and returns an XYZCommand object as a Command.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Model component

API : Model.java

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • exposes a FilteredList<Person> backed by the address book's observable list. Changing its predicate updates the displayed results without removing contacts from the underlying address book.
  • maintains a separate FilteredList<Person> for the latest search, exposed by Model.getRecentFindList() and Logic.getRecentFindPersonList(). Both lists observe the same underlying contacts.
  • stores a UserPrefs object containing GUI settings. This is exposed to the outside as a ReadOnlyUserPrefs object.
  • keeps undo snapshots in an in-memory Deque<AddressBook>; they are not stored in JSON.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Current command and contact model

The MVP includes add, list, find, findproject, project, delete, clear, undo, help, and exit, with same-name support, duplicate-detail validation and persistence. edit was outside the MVP release and now goes beyond it, covering name, phone, email and Telegram username; see Edit command implementation.

The Java package remains seedu.address, and internal names such as AddressBook are retained from AB-3. AddressBookParser dispatches add, edit, delete, clear, find, findproject, list, project, projects, replaceproject, deleteproject, renameproject, sort, undo, help, and exit. Command words are case-sensitive.

AddCommandParser requires exactly one each of n/, p/, e/, tele/, and pr/. It constructs a Person with one initial project. Subsequent project commands append associations. EditCommand can replace the name, phone, email and Telegram username, and always keeps the contact's projects. EditCommandParser accepts n/, p/, e/, and tele/, requires at least one of them, and rejects pr/. Individual project replacement is supported by replaceproject, and removal by deleteproject. renameproject renames or merges a project across all contacts. Unsupported prefixes are not a general extension mechanism: unrecognised text can become part of another field's value, so callers must use the documented grammar.

Value class Current new-input rule and normalisation
Name 1–60 characters, at least one English letter; English letters, digits, spaces, apostrophes, hyphens and periods. Surrounding spaces are trimmed.
Phone Leading +, 3–15 digits with a non-zero first digit; accepted internal spaces and hyphens are removed. No country code is inferred.
Email One @, non-empty dot-separated local parts, and at least two valid domain labels; no whitespace. Stored in lowercase.
TelegramUsername 5–32 Latin letters, digits or underscores; optional leading @ is removed and letters are lowercased.
Project 1–40 Unicode code points after whitespace normalisation; no ISO control characters. Equality ignores case.

JsonAdaptedPerson restores names, phones and emails through their stored-value validation paths, preserving legacy spelling and phone formats. Missing Telegram usernames become TelegramUsername.EMPTY; missing projects become an empty list. These compatibility rules do not make those fields optional in new add input.

Name search and displayed indices

FindCommandParser trims surrounding whitespace and rejects blank input or more than 60 Unicode code points before splitting keywords on whitespace. NameContainsKeywordsPredicate compares lowercase text using Locale.ROOT and matches any keyword as a substring (OR semantics), including partial words. For example, find lex vid can match Alex and David. Each contact appears once in saved order.

Both search commands replace the predicate on the full address book rather than searching only the previous results. delete, edit, and project resolve one-based indices against the displayed list. add, a successful edit, list, and successful undo show all contacts; delete, project, and a failed or unchanged edit retain the active filter. After a mutation, indices can change, so callers must read the current list before using another index.

Recent search results

MainWindow.fillInnerParts() constructs RecentFindPanel using Logic.getRecentFindPersonList() and inserts it into recentFindPanelPlaceholder. RecentFindPanel.fxml defines its ListView<Person> with variable-height cells. Each cell displays a compact VBox containing a Name | Telegram header above project tags, without indices. TelegramUsername.isEmpty() selects the No Telegram Username fallback; otherwise toString() supplies the username with its leading @. The header tooltip contains the full name and displayed handle or fallback. Commands continue to resolve indices exclusively against Model.getFilteredPersonList().

SearchContactDetails gives the projects FlowPane the same projects ID used by PersonCard, reusing the existing tag colors, padding, corners, font, and spacing in DarkTheme.css. The card width follows the cell width so tags wrap within the list. Empty project lists are hidden and unmanaged.

The panel binds its single latest-search label to Logic.recentSearchProperty(). LogicManager owns the read-only string wrapper and updates it after either search command executes, before saving, so the label stays consistent with in-memory results on save failure. The stored value uses Name: or Project: , with query trimming delegated to FindCommandParser.trimSearchInput. Other commands and parse failures leave it unchanged. The label adds Latest search: and exposes the full text in a tooltip.

ModelManager creates the recentFind filtered list once, initially with a predicate that matches no contacts. updateFilteredPersonList(predicate) updates the main list and copies the predicate to recentFind unless it is the PREDICATE_SHOW_ALL_PERSONS constant. Both find and findproject therefore replace the latest search, while list, add, successful edit, and undo can show all contacts without replacing that search predicate. Keeping a separate list with a stable identity allows the panel to observe updates throughout the session.

Recent results are a live filtered view rather than a snapshot. Contact additions, edits, deletions, clearing, and undo update membership and displayed details according to the retained predicate. Invalid search input fails before either predicate changes. Before the first search the list prompts for a search; later an empty list displays No contacts match the latest search.. The predicate is held only in memory, so recent results start empty on each launch and require no storage changes.

MainWindowTest.recentFindResults_updateAndRemainAboveLargerPersonList() verifies the initial empty state, relative size and placement, replacement by a later search, no-match results, and retention after list. It also checks the initial label, name and project search text, preservation after invalid input and list, and the tooltip text.

RecentFindPanelTest checks populated and missing Telegram usernames, header tooltips, project order, and cleanup when cells are reused or results are cleared. Its rendered styling test compares project tags with a PersonCard for background, text color, padding, font, border, and spacing, and verifies wrapping.

Most searched contact and shared latest search

LogicManager owns one session-only SearchHistory, constructed with the unfiltered observable contact list. After either FindCommand or FindProjectCommand executes and saving succeeds, it records the filtered results. Parse failures, command failures and save failures do not increment frequencies. The shared latest search property updates before saving, independently of frequency counts.

SearchHistory maps each full Person value to a frequency and last-search sequence number. Every matching contact earns one count per search; repeated matching keywords do not multiply counts. The sequence is shared by all contacts in a single search. Ranking compares frequency first, then the last-search sequence. Iterating the current unfiltered contact list resolves any remaining draw in contact order, yielding exactly one contact or null. Same-name contacts have separate entries. A no-match search updates recent text without affecting any contact's frequency or recency.

The contact-list listener transfers statistics across replacements without changing their last-search sequence. It handles both single-element edits/project updates and equal-sized snapshot replacements from undo. Contacts already present in the replacement retain their own statistics, so list reordering cannot exchange counts. Removed contacts are pruned. Deletion and clear therefore discard the affected counts permanently; undoing those operations restores contacts without restoring their discarded counts. Undoing an edit or project change preserves counts. Search statistics are not part of the contact undo snapshots, JSON data or user preferences, and reset on restart. The latest search query survives contact mutations until the next executed name or project search.

Logic exposes read-only mostSearchedPersonProperty() and recentSearchProperty(). MainWindow groups the two search sections in an equal-width GridPane, above the numbered Current contact list. Most searched is on the left, with the subtitle Top contact this session; Recent search is on the right. Both content areas align vertically and scroll independently. The horizontal scrollbar of the recent results list is hidden; contact headers truncate with tooltips, while project tags wrap. The latest query appears only once, in RecentFindPanel. SearchContactDetails renders contact headers, Telegram fallbacks, full-text tooltips and wrapping project tags for both features. The favourite shows No contacts searched yet. when no current contact has a count, and its details scroll when needed.

SearchHistoryTest covers frequency, search recency, same-search ordering, namesakes, edits, snapshot restore, reordering, deletion, empty results and session reset. LogicManagerTest covers command integration, Unicode query trimming, repeated keywords, failed searches, storage failure/retry, edits/undo and clear/undo. SearchSummaryUiTest loads the actual FXML and checks distinct latest results and the session favourite, tooltips, equal column widths, aligned content and compact layout at the 450-pixel minimum width.

Removing retired contact fields

Person contains name, phone, email, Telegram username, and an ordered list of projects. Address and tags have been removed from the model, contact cards, and JSON output. AddCommandParser and EditCommandParser recognize the old a/ and t/ delimiters only to reject them with ParserUtil.MESSAGE_REMOVED_CONTACT_FIELDS; this prevents old arguments from becoming another field's value. These delimiter sequences following a space remain reserved in add/edit input.

JsonAdaptedPerson ignores old address/tag properties through the existing Jackson unknown-property configuration. Missing Telegram usernames and projects retain their legacy defaults. Before saving, JsonAddressBookStorage.backupLegacyData inspects the existing file for retired fields and writes its original bytes to a unique sibling .pre-v1.3-<unique suffix>.bak file. It also backs up malformed JSON before replacement. A backup I/O failure propagates before any overwrite. After a successful migration, subsequent saves find no retired properties and create no further backup. Backup files are not part of command undo history.

A file that is well-formed but cannot be loaded, for example because two contacts conflict, may have no retired fields and therefore may not qualify for the migration backup. When MainApp.initModelManager catches the DataLoadingException and starts with an empty address book, it calls Storage#backupAddressBook(), which copies the file to a unique sibling .unreadable-<unique suffix>.bak file before the first save can replace it. If the backup fails, initModelManager rethrows the IOException and init() stops before creating Logic or the UI, so no save can replace the only copy; start() then shows an error dialog asking the user to copy the file somewhere safe and fix the problem, and exits. LinkUp starts with an empty address book only after a successful backup. MainAppTest covers both outcomes. The backup is made only at startup, not on every read, so tests and other callers of readAddressBook do not create backup files.

Regression tests cover legacy loading, the save/load round trip, exact backup contents, repeated saves, backup failure, and former-prefix rejection. Existing edit, project, search, and undo tests exercise the updated contact structure. New add commands require an initial project; legacy contacts can still have an empty project list.

Duplicate contact detection

Two contacts conflict if they share a phone number, an email or a Telegram username. Names and projects are never compared, so contacts may share a name. The rule lives in one place, Person#findConflictWith(Person), which checks phone, email and Telegram username in that order and returns the first clash as a ContactConflict (the clashing field, the value and the existing contact). ContactConflict#getMessage() builds the only user-facing duplicate message. Person#conflictsWith(Person) is the boolean form.

  • Newly entered emails are stored in lower case, but emails saved by older versions keep their case. Email#equals and Email#hashCode therefore compare the lower-cased (Locale.ROOT) text, so a saved Bob@Example.com still clashes with a new bob@example.com. TelegramUsername is already normalised to lower case without @ when it is constructed.
  • Phones are compared in their saved form. New numbers are stored as + followed by digits, so spaces or hyphens never hide a clash. A legacy local number such as 91234567 does not match +6591234567, because LinkUp never infers a country code. An empty Telegram username (TelegramUsername.EMPTY, used by legacy contacts) never matches.
  • UniquePersonList checks every add, setPerson and setPersons call and throws DuplicatePersonException carrying the conflict message. setPerson(target, editedPerson) ignores target, so a contact never conflicts with its own old values, while a clash with any other contact is still caught.
  • Model#findConflict(candidate) and Model#findConflict(candidate, excluded) expose the check. AddCommand uses the first; EditCommand passes the contact being edited as excluded. Both reject a conflict through Command#rejectIfConflicting, before the model is changed. JsonSerializableAddressBook rethrows a conflict found while loading as an IllegalValueException with the same message.
  • The relation is symmetric but not transitive: A may share a phone with B and B an email with C, while A and C do not conflict. It is therefore not an equality. Person#equals remains the all-fields check used to find and remove a contact, which keeps lookup working for contacts with the same name.

Alternatives considered:

  • Keep isSamePerson, redefined as "all fields equal". This would still let two contacts share a phone or email under different names, and it would duplicate equals. It was removed instead.
  • Lower-case every saved email when loading. This would make a case-sensitive comparison enough, but it would silently rewrite emails saved by older versions. Comparing case-insensitively handles both old and new emails.
  • Warn about, rather than reject, a contact with the same name. Names do not identify people, and a warning on every same-name contact would add noise without preventing real duplicates.

Tests build clashes with ConflictTestUtil#clashesWith. EditCommandTest#UNIQUE_FIELD_EDITS lists the editable unique fields (phone, email and Telegram username); when another unique field becomes editable, adding one entry there tests that it is rejected on a clash with a visible or hidden contact, and that the contact's own value is not a clash when another field changes.

Finding contacts by project

The findproject KEYWORD command implements UC02 using the existing filtered contact list.

  1. AddressBookParser routes findproject to FindProjectCommandParser.
  2. The parser removes surrounding whitespace, rejects a blank phrase, and checks the 40-character limit before collapsing internal whitespace. Length is measured in Unicode code points, consistent with the project model. The surrounding-whitespace rule covers the same whitespace and Unicode separator characters as Project.normalize().
  3. ProjectContainsKeywordPredicate uses Project.normalize() and Locale.ROOT to normalise the search phrase once. It checks whether any project returned by Person.getProjects() contains that whole phrase, ignoring case.
  4. FindProjectCommand passes the predicate to Model.updateFilteredPersonList(...) and returns the result count or a specific no-matches message. The UI observes this list and displays the existing contact cards and indices.

The predicate filters contacts rather than collecting a result for each matching project, so a contact appears at most once. Replacing the predicate searches the full underlying address book, even after another search has filtered the displayed list. list restores all contacts; delete continues to use the displayed indices. Search does not change contacts or project associations. LogicManager retains its normal save-after-command behaviour, saving the complete address book rather than just the search results. Invalid input fails during parsing, before the filter or saved data is changed.

Both the search keyword limit and the stored project-name limit are 40 Unicode code points. The search parser checks length before collapsing internal whitespace, whereas Project validates the normalised name. The parser therefore validates the search phrase separately from ParserUtil.parseProject().

Design choices: A separate command preserves the existing name-search behaviour. Whole-phrase substring matching supports partial project names without treating individual words as alternatives. Reusing the model's existing filter avoids introducing a separate project index or changes to storage. The recent-results panel observes the same project predicate through its separate filtered list.

Project association implementation

The project INDEX [MORE_INDICES] pr/PROJECT command extends UC03 to one or more contacts. AddressBookParser delegates to ProjectCommandParser, which splits the index preamble on whitespace, validates every token with ParserUtil.parseIndex, rejects repeated indices, and requires exactly one project prefix. ParserUtil.parseProject reuses shared project validation and normalization.

The sequence diagram below shows a successful execution of project 1 2 pr/Orbital, including how the command validates the complete batch before changing either contact.

`ProjectCommand` copies the displayed contact list before resolving indices. It validates all selections and prepares updated `Person` objects before applying any changes through `Model.setPerson`. A duplicate association or invalid index rejects the whole command, so earlier valid selections are not changed. Duplicate errors list all conflicting contacts by displayed index and name, in input order. Out-of-range indices take precedence over association conflicts; no updates occur in either case. Each replacement appends the project while preserving existing project order and all contact details. Selected contacts are captured before mutation, so changes to filtered results cannot redirect later updates. The active predicate is retained. Contacts outside the selection remain unchanged. The existing `LogicManager` records one snapshot for the entire command and persists the resulting address book. One `undo` restores all affected contacts; rejected commands leave undo history intact. No new storage format is needed. FINE logs record parsing failures, rejected selections and success counts. Tests cover single-contact compatibility, multiple indices, malformed or repeated indices, normalization, validation before mutation, filtered-list changes, persistence, one-step undo and diagnostic output. Manual check: run `findproject Team`, then `project 1 2 pr/Orbital`; verify both selected contacts gain Orbital. Run `undo` once and verify both associations are removed. Run `list` to verify the contact remains saved, then `undo` to restore its project. ### Edit command implementation `edit INDEX [n/NAME] [p/PHONE] [e/EMAIL] [tele/TELEGRAM]` replaces one or more details of the contact at a one-based index in the displayed list. `EditCommandParser` validates each supplied value with the same `ParserUtil` methods as `add` and stores it in an `EditCommand.EditPersonDescriptor`. It reports one problem at a time, in this order: retired `a/` or `t/`, any `pr/` (with `EditCommand.MESSAGE_PROJECT_NOT_EDITABLE`), the index, repeated prefixes (even with identical values), the supplied values (name, phone, email, Telegram username), and finally a missing field. The parser never reads the model. A field left unset in the descriptor is kept exactly as saved, so untouched legacy values (for example a local phone `91234567` or a mixed-case email) are not normalised, and a legacy contact is never forced to supply a Telegram username or project. `EditPersonDescriptor#setTelegramUsername` rejects `TelegramUsername.EMPTY` with an `IllegalArgumentException`: a Telegram username cannot be cleared, so a parser or helper bug fails loudly instead of wiping it. `null` means "not supplied". `EditCommand` also defines `MESSAGE_PROJECT_NOT_EDITABLE`, for the parser to report `pr/`. `EditCommand#execute` checks, in order: 1. The index is within the displayed list, or it reports `Messages.MESSAGE_INVALID_PERSON_DISPLAYED_INDEX`. 2. It builds the complete replacement `Person`: supplied fields replace, omitted fields and the ordered project list are copied. 3. If every saved string (`Name#fullName`, `Phone#value`, `Email#value`, `TelegramUsername#value`) is unchanged, it throws `No changes made.` Saved strings are compared instead of `Person#equals` because `Email#equals` ignores case: re-entering a legacy `Alex@Example.com` as `alex@example.com` is a real change. A Telegram username entered as `@Alice_Tan` normalises to `alice_tan`, so it is unchanged if that is the saved value. 4. `Model#findConflict(editedPerson, personToEdit)` checks the whole address book, including contacts hidden by the filter, and `Command#rejectIfConflicting` reports the first clash. Unchanged values cannot clash, so the no-change check runs first. 5. `Model#setPerson` replaces the contact once and the filter is reset to show all contacts. The activity diagram below shows these checks. Each rejection ends the command before the model changes. Every rejection is a `CommandException` thrown before the model changes. Because `LogicManager` records an undo snapshot and saves only after a command returns normally, a failed or unchanged edit leaves contacts, the filter, the saved file and the undo history as they were, without any change to `LogicManager`. One successful edit, whatever the number of fields, is one undo step. **Alternatives considered:** * *Treat an unchanged edit as a successful command.* It would save the file and push an undo snapshot that undoes nothing, so the next `undo` would appear to do nothing. It was rejected. * *Apply the valid fields and report the invalid ones.* Partial edits are hard to notice and undo, so the whole command is rejected instead. `EditCommandTest` covers each field, legacy values, filtered indices, conflicts with visible and hidden contacts, no-change detection and filter handling. `EditCommandParserTest` covers the parse order above. `EditCommandIntegrationTest` types `edit` commands, including `tele/` and `pr/`, through the real parser, `LogicManager` and JSON storage, checking saved data, reloads, save counts, the filter and undo. ### Project renaming and merging `RenameProjectCommandParser` uses the shared `ArgumentTokenizer` to parse `old/` and `new/` in either order, rejecting missing, blank or repeated arguments and unexpected preamble. Values go through `ParserUtil.parseProject`. Quotes and backslashes remain literal, as in `replaceproject`; a space followed by a recognised prefix is always a delimiter, even inside quotation marks. `RenameProjectCommand.execute` reads the full address book and validates a complete replacement before changing the model. Case-insensitive `Project.equals` identifies memberships, while exact display strings identify actual changes. The replacement preserves contact details (including legacy values), contact order and unrelated project order. For merges, an existing destination association retains its position; the source is removed when both occur. Destination-only contacts also receive the requested spelling. Changed contacts are counted once, and `Locale.ROOT` keeps the displayed count independent of the system locale. Ordinary renames, case-only corrections and merges execute immediately through the same command path. `Model.setAddressBook` installs the replacement without changing the current filter. The live filtered list re-evaluates the renamed contacts, so a project search may gain or lose results. `LogicManager` records one undo snapshot and saves through the normal command flow. The success message mentions `undo`. There is no pending confirmation state or rename-specific branch in `LogicManager`. Case-only changes must never be detected with `AddressBook.equals` or `Person.equals`, because their project comparisons ignore case. The shared persistence and save-failure behaviour described below applies to rename: a failed save leaves the in-memory change and its undo entry available. Tests cover literal quotes and backslashes, Unicode length boundaries, mixed display spelling, hidden contacts, merge overlap/order, filter re-evaluation, locale-independent counts, failed saves, restart, and one undo restoring exact strings. `RenameProjectUiTest` verifies visible project labels after case-only renaming and undo. ### Sort command implementation `sort` puts every saved contact in name order and saves that order. `AddressBookParser` creates a `SortCommand` directly, since the command takes no arguments; extra text is ignored, as for `list` and `clear`. The order is defined once, in `PersonNameComparator`: names are compared in lower case (`Locale.ROOT`), names that differ only in case are ordered by their exact text, and contacts with the same name are ordered by their saved phone value. Phone values are unique (see [Duplicate contact detection](#duplicate-contact-detection)), so the order of any contact list is fully determined. `SortCommand#execute` throws a `CommandException` when there are no contacts (`No contacts saved yet.`) or when they are already in order (`Contacts are already sorted by name.`). Because `LogicManager` records an undo state and saves only after a command succeeds, these cases change nothing and add no undo entry, matching `edit`'s `No changes made.` handling. Otherwise it calls `Model#sortPersons`, which reaches `UniquePersonList#sortPersons`. That uses `FXCollections.sort`, so the UI receives a single reordering change. The filtered list keeps its predicate, so any search results stay displayed in the new order. `sort` is undoable: `LogicManager` stores the previous address book, and `undo` restores the previous order. **Design choices:** * *Reorder and save the list, rather than show a sorted view (e.g. a JavaFX `SortedList`).* Indices then match what is displayed and saved, the order survives a restart, and undo works through the existing snapshot mechanism. The cost is that contacts added later appear at the end until the next `sort`. * *Break ties by exact name, then phone, rather than keeping the existing order.* The result depends only on the contacts, not on their history, which keeps the behaviour predictable and easy to test. ### Undo command implementation The `undo` command restores the address book to the state before the most recent successful command that supports undo and has not already been undone. It supports `add`, `edit`, `delete`, `clear`, `project`, `deleteproject`, `replaceproject`, `renameproject`, and `sort`. Previous states are kept in a stack, so repeated `undo` commands reverse changes in reverse execution order. When `LogicManager.execute(...)` receives a command, it checks `Command.isUndoable()`. For an undoable command, it copies the current address book before execution. If execution succeeds, `LogicManager` saves that copy through `Model.saveUndoState(...)`, pushing it onto `ModelManager`'s `Deque` undo history. Commands that are not undoable and commands rejected during parsing or execution will not be added to the undo history. When `undo` is invoked and undo history is not empty, `LogicManager` first saves `Model.getUndoState()` to storage. If that save fails, the contact list, filter, and history remain unchanged, allowing the user to retry. `UndoCommand` checks `Model.canUndo()` before restoring anything. If a snapshot exists, `ModelManager.undo()` restores the most recent snapshot with `AddressBook.resetData(...)`, removes only that snapshot from the undo history, and updates the filtered person list to show all contacts. If no snapshot exists, the command reports `No command to undo.` The undo history is held only in memory and is not persisted, so it is unavailable after restarting the application. A new undoable command after an undo adds a snapshot of the current state while preserving earlier history. There is no redo command. ### Persistence and save failures Apart from the special undo path above, `LogicManager` saves the complete address book after each command executes successfully, including `find`, `findproject`, and `list`. Parsing and validation failures do not save. The data path is `data/addressbook.json`, relative to the launch folder; `preferences.json` records GUI settings. Both paths are constants in `MainApp`. Shutdown saves preferences, not a separate copy of contact data. A failed save is reported as a `CommandException`, with a separate message for access-denied errors. Ordinary mutations are not rolled back on disk-write failure: the UI can contain an unsaved change and its undo snapshot. After fixing storage, a successful command such as `list` retries saving the current state. This differs from validation failure, which leaves contacts unchanged. ### Deferred features Notes, roles, sorting by project, archiving, and redo are not implemented. The user stories below include backlog ideas; they are not claims about commands available in this release. No archiving design has been implemented yet. -------------------------------------------------------------------------------------------------------------------- ## **Documentation, logging, testing, dev-ops** * [Documentation guide](Documentation.md) * [Testing guide](Testing.md) * [Logging guide](Logging.md) * [DevOps guide](DevOps.md) -------------------------------------------------------------------------------------------------------------------- ## **Appendix: Requirements** ### Product scope **Release boundary:** All ten commands listed in the current command model were in the MVP release. `edit` was excluded from MVP acceptance and has since been extended as post-MVP work. CI exercises Windows, macOS and Linux with Java 25; other OS/JDK combinations are not verified by that matrix. 1. **Environment:** The supported release setup is Windows, macOS or Linux with Java `25` installed. 2. **Capacity:** The system shall support at least 1000 saved contacts without noticeable sluggishness during typical usage. 3. **Performance:** The system shall return results within 2 seconds when searching using name or project for a contact list of up to 1000 contacts. 4. **Usability:** The system shall display a clear success message or a specific error message after every command. 5. **Interaction efficiency:** A user with above-average typing speed for regular English text should be able to complete most tasks faster using commands than using mouse interactions. 6. **Data integrity:** If a command fails because of invalid input, an invalid index, or a duplicate, the system shall leave the contact list unchanged. 7. **Data consistency:** The system shall validate and normalise contact and project data consistently before storing or searching it. 8. **Persistence and reliability:** Contacts should survive restart after a successful save. An unreadable data file is backed up before starting empty; if backup fails, startup stops with an error dialog. Ordinary save failures report an error but may leave unsaved changes in memory, as described above. ### Glossary * **Contact**: A saved record for a project mate, containing their name, contact details, and associated projects. * **Project**: A module project or team that a contact belongs to, such as CS2103T or Orbital. * **Project association**: A link between a contact and a project. A contact can be associated with more than one project. * **Displayed contact list**: The numbered main person list, including results of a search; command indices refer to this list. * **Recent search results**: A smaller, unnumbered view of contacts matching the latest name or project search in the session. * **Index**: A one-based number identifying a contact in the currently displayed contact list. * **Same-name disambiguation**: Using project information to distinguish contacts with identical or similar names. * **Mainstream OS**: Windows, Linux, Unix, or macOS. -------------------------------------------------------------------------------------------------------------------- ## **Appendix: Instructions for manual testing** Use a separate writable test folder with Java 25 and a freshly built `LinkUp.jar`.
